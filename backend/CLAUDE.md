## Project Overview

CCT (Construction Carbon/Cost/Time) - FastAPI backend for construction project management with carbon emission tracking, cost optimization, and schedule management. **Multi-project**: each project owns its tasks, resources, constraints, and optimization runs.

**Stack:** FastAPI + SQLModel + PostgreSQL (asyncpg) + Alembic + Python 3.14

## Architecture

### Layer Pattern
```
Router (API) → Service (Business Logic) → Model (Data)
              ↓
           Schema (Validation/Serialization)
```

### Directory Structure
```
src/
├── app.py              # FastAPI app entry, CORS, router registration
├── config.py           # pydantic-settings configuration
├── database.py         # Async engine, session dependency
├── routers/            # API endpoints (see URL layout below)
├── services/           # Business logic
├── models/             # SQLModel ORM entities
├── schemas/            # Pydantic request/response DTOs
├── dependencies/       # FastAPI dependency injection
│   └── public/         # Shared dependencies (session, pagination, project)
└── utils/              # Shared utilities (parsers, calculators, nsga2_optimizer, query)
```

### Models ↔ Schemas Relationship
Models (`src/models/`) **can** depend on schemas to avoid repetition (e.g., using schema enums as model field types via `PydanticJson`). Schemas must **not** import from models. Keep the dependency direction one-way: models → schemas.

### Schema and Update Semantics

- `Base` contains shared business fields; `Create` adds creation-only fields; table models add ORM-only fields and database configuration; `Resp` adds database-generated fields.
- A field without a Pydantic default is `required` in OpenAPI and must be provided by the client. A Pydantic `default` is an application-layer value used when the field is omitted.
- `T | None` controls whether API validation accepts JSON `null`. Database `nullable` independently controls whether the column can store SQL `NULL`; `server_default` independently controls values generated by the database.
- This project intentionally uses `PUT` for partial updates. Every PUT update must call `model_dump(exclude_unset=True)` so omitted fields remain unchanged while an explicitly supplied `null` is preserved.
- Update fields are optional to provide. Explicit `null` is valid only for fields backed by nullable columns; Update schemas must reject explicit `null` for NOT NULL fields with a 422 validation response.

## Multi-Project Support

Every project-scoped entity has a `project_id` FK → `project.id` (ON DELETE CASCADE). The `ProjectScopeMixin` (in `src/models/mixin.py`) injects this column into models. The `project_id` is **not** part of any schema — it is set on model instances by the router from the URL, not from request bodies.

### URL Layout
| Router | Prefix | Purpose |
|--------|--------|---------|
| `project.py` | `/project` | Project CRUD (no project_id needed) |
| `task.py` | `/projects/{project_id}/task` | Task CRUD, dependencies, critical path |
| `resource.py` | `/projects/{project_id}/resource` | Resource management |
| `resource_usage.py` | `/projects/{project_id}/resource-usage` | Task resource consumption |
| `daily_report.py` | `/projects/{project_id}/daily-report` | Excel import pipeline |
| `optimize.py` | `/projects/{project_id}/optimize` | NSGA-II optimization, resource constraints |

### Project-Scoped Query Pattern
Use `CurrentProject` (`src/dependencies/public/project.py`) to extract `project_id` from URL; it returns a `ScopedProject` (a `Project` subclass with `id: int` rather than `id: int | None`).

For data queries, use the two helpers in `src/utils/query.py`:
- `project_filter(stmt, Model, project_id)` — adds `WHERE project_id = :pid` to a `select()`
- `project_count_filter(stmt, Model, project_id)` — same but for `select(func.count()).select_from(Model)` (preserves `SelectOfScalar[int]` typing)

Apply project filter at the start of every router/service query that touches a project-scoped model.

### Project-Scoped Unique Constraints
| Table | Constraint |
|---|---|
| `task` | `UNIQUE(project_id, code)` (was globally UNIQUE on code) |
| `resource` | `UNIQUE(project_id, name)` (was globally UNIQUE on name) |
| `task_resource_usage` | `UNIQUE(project_id, task_id, resource_id, usage_date)` |
| `resource_constraint` | `UNIQUE(project_id, resource_id)` |

The global `task_code_seq` sequence is still shared; since `(project_id, code)` is now unique, the same `AUTO-N` can appear in multiple projects.

## Key Entities

- `Project` — top-level container; `id`, `name`, `description`, `is_active`
- `Task` — Construction tasks with dependencies (`project_id`, `code`, `name`, `duration`, `completed`)
- `TaskDependency` — M:N self-ref on `task`, has its own `project_id`
- `Resource` — Per-project (not shared); `(project_id, name)` unique
- `TaskResourceUsage` — Per-task-per-day consumption; `(project_id, task_id, resource_id, usage_date)` unique
- `ImportBatch` — Daily report import tracking, scoped to a project
- `ResourceConstraint` — Per-project resource daily usage limits
- `OptimizationRun` — NSGA-II run record, project-scoped
- `ParetoSolution` — Pareto-optimal solutions, project-scoped (for direct project queries without joining through run)

## Optimization System (NSGA-II)

**Four construction modes** (integer codes 0-3): STANDARD, ACCELERATED, LOW_CARBON, ACCELERATED_LOW_CARBON.

**Optimization objectives:** Minimize cost (present value), minimize carbon emissions, minimize duration.

**Architecture:**
- `src/utils/nsga2_optimizer.py` — NSGA-II core (pymoo); `run_optimization(request, callback)` runs sync in a thread pool
- `src/services/optimization_adapter.py` — `load_optimization_data(session, project_id)` loads ONLY the project's data and adapts to NSGA2 input types
- `src/services/optimization_consumer.py` — Async event consumer; reads from `asyncio.Queue` written by sync optimizer thread, writes results to DB
- `src/routers/optimize.py` — Passes `project.id` to `load_optimization_data`; `_background_worker` gets `project_id` from the run record

**Constraint violation fields** (`max_usage`, `real_usage`, `overage`) are `float`, not `int`.

See `核心算法.md` for algorithm formulas.

- Alembic for all migrations (NOT `SQLModel.metadata.create_all()`)
- All DB operations are async with `AsyncSession`
- Use `TimeStampMixin` for auto `created_at`/`updated_at`
- `ProjectScopeMixin` for any project-scoped model (after `TimeStampMixin`, before schema bases)

### Dependency Injection
- `session: AsyncSession = Depends(get_db_session)` for DB access
- `project: CurrentProject = Depends(...)` for project-scoped routes (returns `ScopedProject`)
- Stateless services via `@lru_cache` factory or `staticmethod` (TaskDependencyService, TaskSchedulerService, TaskCodeService)
- Stateful services accept `project_id` in constructor (DailyReportService, ResourceUsageService)

## Construction Modes (Optimization)

| Mode | Code | Duration | Cost | Carbon |
|------|------|----------|------|--------|
| STANDARD | 0 | Normal | Normal | Normal |
| ACCELERATED | 1 | Reduced | +1.5×ΔT/T (machinery + labor) | Living carbon reduced |
| LOW_CARBON | 2 | Normal | +20% machinery | -40% |
| ACCELERATED_LOW_CARBON | 3 | Reduced | Combined | Combined |

**Key formulas:**
- Accelerated cost: `C_G = C_N × (1 + 1.5 × ΔT/T_N)`
- Low-carbon carbon: `E_G = 0.6 × E_N` (40% reduction)
- Present value: Monthly settlement (every 30 days) with IRR discount
